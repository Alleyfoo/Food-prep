## Tastings can be recorded from the app (2026-11-21)
- **Scout → *Record a tasting*** (`streamlit_app._tasting_form`): the form
  calls `tasting.record_trial(..., yaml_path=tasting.tastings_path())`.
- **`tasting.append_trial_yaml` is the only writer** of `tastings.yaml`. It
  checks that the whole file plus the new block parses strictly and

## Scout scoping fixed (2026-11-21, `929e8b3`)
Item 1 below is done, deterministically and without any language model, at the
user's request. How it works now:
- **`serving_forms`** (vocabularies.yaml) — what a state *is* on the plate.
  Derived from the technique via each form's `techniques:` list and stored in
  `component_state_profiles.serving_form`. Override per state with
  `state_profile.form`. A technique in zero or two forms is a load error.
- **`ingredient_families`** — `family:` on the 11 ingredients that own states
  (butter has none on purpose; it would make "add more butter" a leak).
- **Every rule declares `forms` + optional `families`, or exact `states`.**
  An unscoped rule fails the build.
- **`{state}` placeholder** in rule prose/protocols renders as "roasted
  broccoli", "tomato soup" etc. (`query.state_label`). Use it whenever a rule
  travels across ingredients.
- **Wording guard** (`query._wording_leak`): a hypothesis is rejected if its
  text names another state-owning ingredient, or if its shared function /
  ratio / smallest test names another form's keyword (ingredient names like
  "soy sauce" are stripped first). Risks and failures are exempt from the form
  check because "may taste like soup" is a comparison.
  `tests/test_scout_scope.py::test_wording_guard_catches_nothing_in_shipped_rules`
  keeps its catch empty, so **fix the rule's scope, never loosen the test**.
- A rule never replaces the state's own ingredient (no peach-for-tomato on
  tomato); one card per candidate per state (a recorded tasting wins the tie).
- **344 → 98 live hypotheses.** Roasted broccoli: 13 → 6. The brown butter
  trial still attaches.

Silent data bugs this uncovered, now load errors:
- PyYAML kept the last of two duplicate keys. A lost `- id:` line had merged
  `soft_egg_for_butter_on_mashed_potato` over
  `tahini_for_cheese_on_caramelized_onion`. `load_yaml` now refuses duplicates.
- State flavour/texture tags were unvalidated (trap #1 from August):
  `savory` (boiled potato) meant the dill rule never reached boiled potato.
  `firm`, `jammy`, `spoonable` and `liquid` were added to the textures

### The novelty pass has been run (`aa267de`)

`F:\download\google\CulinaryDB` (not in the repo). Cached in

**Ten of those eleven were noise** (`8491f12`). miso is in 0.23% of recipes
and rutabaga 0.14%, so they are expected to co-occur **0.15 times** — finding
none is what chance predicts, not a discovery. `novelty_class` now takes the
expected count and returns `underpowered` below 3 expected co-occurrences.

    not_observed 1 · underpowered 10

**The one real finding: apricot on braised cabbage** — expected 8.56,
observed 0. The corpus had every chance and did not show it.

Cached novelty is **derived**, unlike tastings: an observation whose ontology
reference disappears is *dropped*, not raised on. Committed only because the
corpus cannot travel with the app. Tests that measure a deliberately sparse
corpus must build with `novelty_path=None`.

**What the corpus cannot do**: it is recipe→ingredient links only — no
instructions, no quantities, and it is **state-blind** (roasted and raw
broccoli are one entity). So it can never fill `application`, and presence is
not evidence: counts are raw, with no lift over base rate. It pairs mango
lassi with capers once, in a crab parfait.

**Do not buy a bigger corpus.** Rare-vs-rare pairs need ~1M recipes to become
measurable, and those are exactly what Scout proposes. The corpus already has
ample power where *routes* live — garlic 35%, lemon 9.1%, soy 6.6%, yogurt
2.2% — and none where Scout candidates live (miso/tahini ~0.25%). Point it at
routes, not novelty.

**Next on this thread**: a lift-based miner for *combinations* (2–4 fillers
co-occurring above chance) to propose route candidates. `cooccurrence()` is
strictly pairwise today. The corpus proposes elements; a cook assigns states
and writes the `fit_reason` — which is exactly how `flavour_route_states` is
already shaped.

### Pairings know *when* a filler meets the food (`cbb1622`)
The user's observation: roasting broccoli in olive oil, butter or dry is
barely distinguishable; dressing steamed broccoli with garlic confit is the
dish. `pairings.application` now records `medium | dressing | finish |
unspecified`. Dressings lead the suggestions, media sort last and render
dimmed.

**Heat type is not a proxy** — an attempt to auto-classify labelled
butter-on-steamed-broccoli a cooking medium, when you steam in water and the
butter arrives afterwards. 24 of 303 hand-classified; **279 remain
`unspecified` deliberately**, and that number is the measurement: it is how
much of the catalogue is single-filler noise.

### Known gap: no secondary transformations
Smashed potato — boil, smash, then roast — **cannot be modelled**.
`transformations` has no input component (every one starts from the raw
ingredient) and `UNIQUE (ingredient_id, technique_id)` allows only one
`roast` per ingredient. `secondary_transformation` is declared in
`vocabularies.yaml` and used nowhere: the gap was anticipated, never built.
Journeys have `transitions`, which is the nearest existing machinery.

### The bigger claim behind both
The perceptible unit is **(state × dressing-combination)** — and a
combination applied to a state is precisely what a flavour route is. The
catalogue is **303 pairings to 3 routes**, inverted relative to where the
signal is. That reframes the route gap from a backlog item to the main one.

### Butter has states now (`79ea137`)
The user pointed out that brown butter is not an ingredient you buy — it is
what butter becomes when its milk proteins are held on heat. The ontology had
`butter`, `brown_butter`, `ghee`, `garlic_butter` as four unrelated
ingredients and **no butter state at all**, which is the project's own
category error: broccoli got four states, butter got none.

Butter is now `kind: both` with two transformations that are **opposite moves
on the same part of it**: `brown` cooks the milk proteins, `clarify` removes
them. That is why they are not interchangeable and why ghee keeps for months.
`brown_butter` and `ghee` remain filler ingredients as well — the cabbage /
sauerkraut two-entry shape — so existing pairings still resolve.

`garlic_butter` → **`garlic_confit`** (alias kept): the user's is whole cloves
slow-roasted ~2h in ghee, which cannot brown. Dimensions corrected
pungent → aromatic.

**The same question is open for other compound fillers.** If brown butter was
a state wearing an ingredient's clothes, check the rest before trusting them.

### 🎉 The first tasting is recorded (`7095799`)
**Brown butter on roasted broccoli — verdict `works`.** The first physical
result in the project. The "one ingredient, two truths" milestone and the
**README rewrite are no longer blocked** (Phase 8's exit condition is five

Recording it exposed a gap worth knowing about: trials only ever lived in the
**gitignored** database, and the app builds in memory from YAML every start —
so a trial was invisible in the UI and lost on a fresh clone.
`_preserve_tasting_trials` only protected a rebuild of an existing local file.
Trials now live in **`src/foodprep/data/tastings.yaml`**, loaded like every

add a second trial rather than editing the first.

The trial was later **annotated, not rewritten** (append-only): the verdict
stands, but what it lost to is garlic *confit*, not garlic butter — browned
proteins against no proteins, not two seasonings of one fat.

controlled test, so ratio and temperature read "not measured" rather than
borrowing the protocol's numbers. And **garlic butter gets no trial** — it is
already a Cook pairing at high confidence, never a hypothesis, and
`tasting_trials` requires an `analogy_id`. Only hypotheses can be tried; the
comparison lives in the brown butter trial's observations.

### Two traps for the next agent
1. **Only the active tab renders now.** Streamlit garbage-collects the state
   of any widget it did not draw, so **every new input widget needs an
   explicit `key=`** *and* an entry in `_STICKY_WIDGETS` (or a
   `_STICKY_PREFIXES` match for dynamically keyed ones).
   `tests/test_ui_state.py` parses the app and fails if you forget.
   **Never persist a button key** — Streamlit then refuses to build the
   button, and it only bites on the *second* visit to that tab.
2. **Do not use `st.pills`.** AppTest cannot serialize a single-select pill
   group (it walks the value string character by character) and every
   subsequent `.run()` throws — it would cost the whole smoke-test workflow.

cancel a trailing `<p>`'s margin. **Our custom HTML ends in `<div>`s**, so
that -1rem ate 16px out of whatever followed — eight blocks were clipped and
the availability heading sat behind its own multiselect. Cancelled in
`design.css` for containers that do not end in a paragraph. If a new custom
block ever overlaps the next element, this is why.
